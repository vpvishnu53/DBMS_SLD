---------------------------------------------------------------------
 A2. RELATIONSHIP SETS
---------------------------------------------------------------------
 Crow's-foot ends as drawn in the diagram. The symbol written next to an
 entity says how many of THAT entity go with one of the other entity:
   ||  exactly one        o|  zero or one
   |<  one or many        o<  zero or many
 The only attribute on a relationship is quantity_used on "uses".

  1. employs       DEPARTMENT || ---- |< EMPLOYEE      (1:N)
      DEPARTMENT: exactly one   |   EMPLOYEE: one or many
      every employee works in exactly one department; a department has one or more employees
      implemented as: EMPLOYEE.dept_id  NOT NULL

  2. logs_into     EMPLOYEE o| ---- || HOMEPAGE      (1:1)
      EMPLOYEE: zero or one   |   HOMEPAGE: exactly one
      every employee has exactly one login; a login belongs to at most one employee
      implemented as: EMPLOYEE.username  NOT NULL UNIQUE -> HOMEPAGE

  3. registers_on  CIVILIAN o| ---- || HOMEPAGE      (1:1)
      CIVILIAN: zero or one   |   HOMEPAGE: exactly one
      every citizen has exactly one login; a login belongs to at most one citizen
      implemented as: CIVILIAN.username  NOT NULL UNIQUE -> HOMEPAGE

  4. accesses      COMPANY o| ---- || HOMEPAGE      (1:1)
      COMPANY: zero or one   |   HOMEPAGE: exactly one
      every company has exactly one login; a login belongs to at most one company
      implemented as: COMPANY.username  NOT NULL UNIQUE -> HOMEPAGE

  5. supervises    EMPLOYEE || ---- o< ZONE      (1:N)
      EMPLOYEE: exactly one   |   ZONE: zero or many
      every zone has exactly one supervisor; an employee supervises zero or more zones
      implemented as: ZONE.emp_id  NOT NULL

  6. handles       EMPLOYEE o| ---- o< COMPLAINT      (1:N)
      EMPLOYEE: zero or one   |   COMPLAINT: zero or many
      a complaint is handled by zero or one employee; an employee handles zero or more complaints
      implemented as: COMPLAINT.handled_by  nullable

  7. assigned_to   EMPLOYEE || ---- o< WORK_ORDER      (1:N)
      EMPLOYEE: exactly one   |   WORK_ORDER: zero or many
      every work order is assigned to exactly one employee; an employee has zero or more work orders
      implemented as: WORK_ORDER.emp_id  NOT NULL

  8. submits       CIVILIAN || ---- o< COMPLAINT      (1:N)
      CIVILIAN: exactly one   |   COMPLAINT: zero or many
      every complaint is submitted by exactly one citizen; a citizen submits zero or more
      implemented as: COMPLAINT.citizen_id  NOT NULL

  9. executes      COMPANY o| ---- o< WORK_ORDER      (1:N)
      COMPANY: zero or one   |   WORK_ORDER: zero or many
      a work order is executed by zero or one contractor company; a company executes zero or more
      implemented as: WORK_ORDER.license_no  nullable

 10. scheduled_in  ZONE || ---- o< WORK_ORDER      (1:N)
      ZONE: exactly one   |   WORK_ORDER: zero or many
      every work order is scheduled in exactly one zone; a zone has zero or more work orders
      implemented as: WORK_ORDER.zone_id  NOT NULL

 11. contains      ZONE || ---- o< FEEDER_PILLAR      (1:N)
      ZONE: exactly one   |   FEEDER_PILLAR: zero or many
      every feeder pillar is in exactly one zone; a zone contains zero or more feeder pillars
      implemented as: FEEDER_PILLAR.zone_id  NOT NULL

 12. located_in    ZONE || ---- o< STREETLIGHT      (1:N)
      ZONE: exactly one   |   STREETLIGHT: zero or many
      every streetlight is in exactly one zone; a zone has zero or more streetlights
      implemented as: STREETLIGHT.zone_id  NOT NULL

 13. deployed_in   ZONE || ---- o< SENSOR      (1:N)
      ZONE: exactly one   |   SENSOR: zero or many
      every sensor is deployed in exactly one zone; a zone has zero or more sensors
      implemented as: SENSOR.zone_id  NOT NULL

 14. powers        FEEDER_PILLAR || ---- |< STREETLIGHT      (1:N)
      FEEDER_PILLAR: exactly one   |   STREETLIGHT: one or many
      every streetlight is powered by exactly one feeder pillar; a feeder powers one or more lights
      implemented as: STREETLIGHT.cabinet_id  NOT NULL

 15. has           STREETLIGHT || ---- o< SENSOR      (1:N)
      STREETLIGHT: exactly one   |   SENSOR: zero or many
      every sensor is mounted on exactly one streetlight; a streetlight has zero or more sensors
      implemented as: SENSOR.pole_id  NOT NULL

 16. receives      STREETLIGHT o| ---- o< COMPLAINT      (1:N)
      STREETLIGHT: zero or one   |   COMPLAINT: zero or many
      a complaint is about zero or one streetlight; a streetlight receives zero or more complaints
      implemented as: COMPLAINT.pole_id  nullable

 17. requires      STREETLIGHT o| ---- o< WORK_ORDER      (1:N)
      STREETLIGHT: zero or one   |   WORK_ORDER: zero or many
      a work order requires zero or one streetlight; a streetlight has zero or more work orders
      implemented as: WORK_ORDER.pole_id  nullable

 18. resolves      WORK_ORDER o| ---- o< COMPLAINT      (1:N)
      WORK_ORDER: zero or one   |   COMPLAINT: zero or many
      a complaint is resolved by zero or one work order; one work order resolves zero or more complaints
      implemented as: COMPLAINT.work_order_id  nullable

 19. generates     WORK_ORDER || ---- o| BILLING      (1:1)
      WORK_ORDER: exactly one   |   BILLING: zero or one
      every bill belongs to exactly one work order; a work order generates zero or one bill
      implemented as: BILLING.work_order_id  NOT NULL UNIQUE

 20. uses          WORK_ORDER o< ---- o< SPARE_PARTS      (M:N)
      WORK_ORDER: zero or many   |   SPARE_PARTS: zero or many
      a work order uses zero or more parts; a part is used by zero or more work orders
      implemented as: junction table WORK_ORDER_PART(work_order_id, part_id, quantity_used)

 21. records       STREETLIGHT || ---- o< ENERGY_LOG      (1:N)
      STREETLIGHT: exactly one   |   ENERGY_LOG: zero or many
      every energy log belongs to exactly one streetlight; a light has zero or more logs (identifying)
      implemented as: ENERGY_LOG.pole_id  NOT NULL, part of PK (pole_id, log_number)

 Not enforced on purpose: the "one or many" minimum in #1 (every department
 has an employee) and #14 (every feeder powers a light). A foreign key cannot
 require a parent to have children, and enforcing it would make it impossible
 to add a new department or feeder pillar before its first employee or light.


#####################################################################
 PART B - THE WEBSITE / ORACLE DATABASE (what was actually built)
#####################################################################

 The ER diagram is mapped to 21 Oracle tables in schema SLMS:
   - 14 tables for the entity sets
   - 5 tables for multivalued attributes
   - 1 junction table for the M:N relationship "uses"
   - 1 implementation table, EMAIL_OTP (sign-up verification codes; not an ER entity)

 Mapping rules used:
   * Composite attributes are flattened into plain columns
       Name -> first_name, middle_name, last_name
       Address -> street, city, state, pincode
       location -> latitude, longitude
   * Multivalued attributes get their own child table
   * Derived attributes are NOT stored; they are computed in SQL views
   * 1:N relationships become a foreign key on the "many" side;
     "exactly one" (||) on the other end -> NOT NULL, "zero or one" (o|) -> nullable
   * 1:1 relationships (logs_into, registers_on, accesses) put the foreign key
     on the side that MUST take part (EMPLOYEE / CIVILIAN / COMPANY), so it can
     be NOT NULL; UNIQUE keeps it one-to-one
   * "uses" (M:N) becomes the table WORK_ORDER_PART
   * ENERGY_LOG's primary key is (pole_id, log_number)
 (Section A2 lists where each relationship is stored.)

 B3. ATTRIBUTES THE WEBSITE ADDED BEYOND THE DIAGRAM
---------------------------------------------------------------------
   HOMEPAGE.user_type        which kind of owner: EMPLOYEE / CIVILIAN / COMPANY
                             (a trigger checks the owner's table matches it)
   HOMEPAGE.is_active        lets an admin disable a login
   HOMEPAGE.created_at       account creation time
   HOMEPAGE.last_login_at    last successful sign-in
   WORK_ORDER_PART.quantity_used   how many of a part a work order used
   EMAIL_OTP (whole table)   one-time codes that verify a new citizen's email before
                             the account is created; stores only an HMAC of the code,
                             with expiry, attempt count and when it was used
   Foreign-key columns that store the relationships (listed in A2).
   Child tables for the multivalued attributes (EMPLOYEE_EMAIL, etc.).

---------------------------------------------------------------------
 B4. CHANGES MADE AFTER CHECKING THE DIAGRAM'S CROW'S-FOOT SYMBOLS
---------------------------------------------------------------------
   #18 resolves      was reversed. Now: one work order resolves many complaints
                     (COMPLAINT.work_order_id). Dispatching a complaint also
                     attaches other open complaints about the same pole.
   #5  supervises    ZONE.emp_id is now NOT NULL (every zone has a supervisor).
   #7  assigned_to   WORK_ORDER.emp_id is now NOT NULL (every job has an employee).
   #16 receives      COMPLAINT.pole_id is now optional (zero or one streetlight).
   #2-4 logins       every employee, citizen and company now has exactly one
                     login; the key moved from HOMEPAGE to the owner's table.
                     The login is created with its owner and deleted with it.
